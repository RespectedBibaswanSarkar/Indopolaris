# Working notes for IndoPolaris

## Commands

```bash
npm run setup          # placeholders + prisma generate + migrate + seed
npm run dev            # Next dev server
npm run verify         # typecheck + lint + build + smoke test
```

Database scripts: `db:generate`, `db:migrate`, `db:migrate:dev`, `db:seed`,
`db:reset`, `db:studio`, `db:verify-constraints`, `db:pglite`.

## Conventions

- **This is Next.js 16, not the Next.js in general knowledge.** APIs and
  conventions differ. `node_modules/next/dist/docs/` ships the full docs —
  read the relevant guide before writing code, and check
  `02-guides/upgrading/version-16.md` for removals. Examples of things that
  have already bitten this repo:
  - `next build` no longer runs ESLint; `next lint` was removed. Lint is
    `npm run lint`.
  - The `eslint` key is gone from `next.config.ts`.
  - Turbopack is the default bundler; a `webpack` key is a hard build error.
  - `middleware` is renamed `proxy`.
  - `LayoutProps<"/">` is a generated global type for route props.
- **Prisma 7**: no bundled query engine — a driver adapter is required
  (`@prisma/adapter-pg`). The `prisma-client` generator emits TypeScript
  source into `src/generated/prisma`, which is gitignored and regenerated by
  `postinstall`. Prisma config lives in `prisma7.config.ts`, not
  `package.json`.
- **Database integrity lives in SQL, not the Prisma schema.** Prisma cannot
  express `CHECK` constraints, so the rules the spec depends on are appended to
  `prisma/migrations/*/migration.sql`. If you add a rule, add it there *and* a
  negative test in `scripts/verify-constraints.ts`.
- Full-text search is the `indopolaris_search()` / `indopolaris_facet_counts()`
  SQL functions in `prisma/migrations/1_search/`. Snippets come back as plain
  text on purpose — never pipe them into `dangerouslySetInnerHTML`.
- Pages that read live data call `await connection()` (from `next/server`)
  before the query, so `next build` succeeds with no database available.

## Phase status

Phases 1–2 complete (scaffold, ML service, Section 6 bandit). Remaining: design
system, public outreach mode, researcher/data mode, admin CMS + auth, AI
pipeline, a11y/i18n, polish + README.

Four things that cost time and will cost it again:

- `scripts/with-db.mjs` starts PGlite but does **not** migrate or seed. Use
  `npm run verify:all` (which does both) rather than assuming a throwaway
  database starts from the schema the tests expect. PGlite also holds **one**
  connection at a time and wedges under concurrent access — if a Python script
  and the ML service both want it, restart `npm run db:pglite`.
- npm scripts do **not** load `.env`. Anything Python-side that needs
  `DATABASE_URL` (training, the bandit simulator) silently degrades to the
  uniform prior and still exits 0. `ml:simulate` goes through `with-db.mjs`
  for exactly this reason; do not bypass it.
- The ML corpus is real but **out of domain**: NASA GES DISC Earth-science
  publications, 2,326 records / 21 labels, and accuracy 0.4448 / macro-F1
  0.4518 is the honest number. The equal-weight soft-voting ensemble is
  *worse than LogisticRegression alone* (0.4950/0.5071) — see README
  "Training corpus and honest numbers" before quoting a metric. The 21 NASA
  labels are not NCPOR's 6 seeded disciplines; nothing maps them automatically.
- Never let a caller retry `POST /feedback`. A retried POST writes a second
  `EngagementEvent` and a second `alpha += reward`, permanently skewing that
  arm. `classify` retries; feedback must not.
